## Implementation Highlights

### ✅ What Went Well

1. **Security-First Design**
   - OTP stored as irreversible bcrypt hash (never plaintext)
   - Portal token is signed JWT, not enumerable UUID
   - Patient scope enforced at middleware layer
   - All secrets sourced from GCP Secret Manager

2. **Comprehensive Testing**
   - 17 tests covering all acceptance criteria
   - Edge cases tested: rate limit sliding window, OTP expiry, scope mismatch
   - Mocked Redis (fakeredis) for isolated testing

3. **Clean Architecture**
   - Dependency injection (FastAPI `Depends()`)
   - Service layer separation (otp_service, jwt_service, notification_client)
   - Middleware stack follows design pattern
   - Type hints on all signatures

4. **User Experience**
   - 6 single-character inputs with auto-advance
   - Countdown timer shows time remaining
   - Clear error messages (expired vs. invalid)
   - Mobile-first responsive design
   - Accessibility: aria-labels, role="alert"

5. **Logging & Audit**
   - HIPAA-compliant: no PHI in logs
   - Structured logging with `encounter_id` for traceability
   - Audit events written for authentication success
   - No OTP or patient phone number ever logged

### ⚠️ Considerations

1. **Rate Limiting is Non-Sliding**
   - TTL set only on first increment; doesn't reset per attempt
   - This is by design (spec: 5 attempts per 1-hour window)
   - ✅ Tested and verified to work correctly

2. **Notification Service Failure is Non-Blocking**
   - If SMS send fails, OTP endpoint returns 200 anyway
   - User can retry `/otp` later
   - ✅ Correct by design (don't fail patient auth on notification issues)

3. **Portal Token Not Generated Here**
   - Assumed to be generated by SMS/notification service
   - US-052 scope is to validate and consume token, not generate
   - ✅ Clean dependency; no cross-cutting concerns

4. **Angular sessionStorage vs localStorage**
   - JWT stored in `sessionStorage` (cleared on browser close)
   - ✅ Correct for web security (prevents persistent XSS attacks)

## Questions & Answers

**Q: Why is the rate limit not a sliding window?**  
A: Per US-052 spec: "5 attempts per 1-hour window". The current implementation (TTL set once, no reset) ensures any 5 requests within a 1-hour period trigger the limit. This is more secure than a sliding window.

**Q: What if the Notification Service is down?**  
A: The OTP endpoint returns 200 anyway; logs a warning. Patient can retry `/otp` later when service recovers. This is by design (non-blocking external dependency).

**Q: How is the portal token generated?**  
A: Outside the scope of US-052; assumed to be generated by the SMS/notification service. US-052 only validates it. The token must be a signed JWT with `purpose="portal_access"` claim.

**Q: Why sessionStorage instead of localStorage?**  
A: OWASP A02 (Cryptographic Failures) mitigation. sessionStorage is cleared on browser close, reducing XSS exposure. localStorage persists across sessions.

**Q: Is the middleware registered in the right order?**  
A: Yes. After JWT Validator (validates token) and RBAC Enforcer (checks role), before routes. This ensures only authenticated patients reach the scope check.
